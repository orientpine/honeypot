# Question Banks (Korean) — 4 Domain Lenses × 6 Question Types

`SKILL.md` 본문의 **Inline Matrix Taxonomy**가 클러리티 차원(rows)을 결정한 후, 도메인 렌즈(columns)에 따라 이 파일에서 적절한 질문 패턴을 조회합니다.

원본: `plugins/general-agents/agents/interview.md` v1.0.0의 Phase 2.1–2.4 한국어 질문 은행 (24 questions)을 그대로 보존하여 도메인 lens 별로 정리. AskUserQuestion 사용 시 2-4개 옵션과 "직접 설명" 탈출구 옵션을 추가하세요.

---

## Lens 1 — 기술 구현 (Technical Implementation)

**핵심 탐구 영역**: 아키텍처, 패턴, 의존성, 확장성, 성능

| 질문 유형 | 질문 패턴 |
|----------|----------|
| **아키텍처 결정** | 이 기능이 10배 규모로 확장되어야 한다면, 현재 설계의 어떤 부분이 병목이 될까요? |
| **의존성 관리** | 외부 라이브러리/서비스가 중단되면 어떤 대안 전략이 있나요? |
| **데이터 흐름** | 이 데이터가 잘못된 상태로 들어오면 시스템은 어떻게 복구해야 하나요? |
| **상태 관리** | 동시에 여러 사용자가 같은 리소스를 수정하면 어떻게 처리하나요? |
| **테스트 전략** | 이 기능에서 가장 테스트하기 어려운 부분은 무엇이고, 어떻게 검증할 건가요? |
| **기술 부채** | 빠른 구현을 위해 나중에 리팩토링이 필요할 것으로 예상되는 부분은? |

### 매핑된 클러리티 차원

| 차원 | 적용 우선순위 |
|---|:---:|
| `intent` | 낮음 (기술은 의도의 표면) |
| `outcome` | 높음 (기술 결과 = 측정 가능한 동작) |
| `scope` | 높음 (어떤 컴포넌트가 영향?) |
| `constraints` | 매우 높음 (규모/성능/의존성) |
| `success` | 높음 (수용 기준 = 기술 명세) |
| `context` | 매우 높음 (브라운필드의 경우 코드베이스) |

## Lens 2 — UI/UX (User Experience)

**핵심 탐구 영역**: 사용자 흐름, 엣지 케이스, 접근성, 에러 처리

| 질문 유형 | 질문 패턴 |
|----------|----------|
| **사용자 멘탈 모델** | 사용자가 이 기능에 대해 가질 수 있는 잘못된 기대는 무엇인가요? |
| **실패 시나리오** | 작업이 실패했을 때 사용자가 스스로 문제를 해결할 수 있는 정보를 어떻게 제공하나요? |
| **극단적 사용자** | 기술에 익숙하지 않은 사용자가 막힐 수 있는 지점은 어디인가요? |
| **상태 피드백** | 오래 걸리는 작업 중 사용자가 진행 상황을 어떻게 알 수 있나요? |
| **데이터 손실** | 사용자가 실수로 중요한 데이터를 삭제하면 복구할 수 있나요? |
| **접근성** | 키보드만 사용하는 사용자도 모든 기능을 이용할 수 있나요? |

### 매핑된 클러리티 차원

| 차원 | 적용 우선순위 |
|---|:---:|
| `intent` | 매우 높음 (사용자가 왜 이걸 원하는가?) |
| `outcome` | 매우 높음 (사용자 경험 결과) |
| `scope` | 중간 (어떤 사용자 흐름?) |
| `constraints` | 중간 (접근성/디바이스) |
| `success` | 매우 높음 (UX 수용 기준) |
| `context` | 낮음 (UI는 종종 그린필드) |

### 스킵 조건
- CLI 도구, 백엔드 전용 작업, 데이터 처리 등 UI가 없는 경우 이 lens를 스킵

## Lens 3 — 우려사항 (Concerns & Risks)

**핵심 탐구 영역**: 보안, 성능, 유지보수성, 규정 준수

| 질문 유형 | 질문 패턴 |
|----------|----------|
| **보안 위협** | 악의적 사용자가 이 기능을 악용하는 가장 그럴듯한 시나리오는? |
| **성능 저하** | 데이터가 예상보다 10배 많아지면 어떤 부분이 먼저 느려질까요? |
| **장애 전파** | 이 컴포넌트가 실패하면 다른 어떤 기능에 영향을 주나요? |
| **비용 폭주** | 예상치 못한 사용량 증가 시 비용이 급격히 증가할 수 있는 부분은? |
| **규정 준수** | 개인정보 보호나 규정 준수와 관련해 고려해야 할 사항이 있나요? |
| **기술 종속** | 특정 벤더/기술에 지나치게 의존하게 되는 부분이 있나요? |

### 매핑된 클러리티 차원

| 차원 | 적용 우선순위 |
|---|:---:|
| `intent` | 낮음 (우려는 의도보다 부수적) |
| `outcome` | 중간 |
| `scope` | 매우 높음 (어떤 위험이 in-scope?) |
| `constraints` | 매우 높음 (규정/SLA) |
| `success` | 중간 (위험 수용 기준) |
| `context` | 높음 (브라운필드 위협 모델) |
| `non_goals` | 매우 높음 ("이 위험은 받아들이지 않는다") |
| `decision_boundaries` | 높음 (보안 결정은 누가 내리는가?) |

### 스킵 조건
- 단순한 리팩토링이나 문서 작업인 경우 간소화 (1-2 질문만)

## Lens 4 — 트레이드오프 (Tradeoffs)

**핵심 탐구 영역**: 복잡도 vs 단순함, 시간 vs 품질, 유연성 vs 성능

| 질문 유형 | 질문 패턴 |
|----------|----------|
| **MVP 범위** | 첫 버전에서 반드시 빠져야 하는 기능과 반드시 있어야 하는 기능은? |
| **완벽 vs 배포** | 80% 완성도로 빨리 배포하는 것과 100% 완성 후 배포 중 어느 것이 더 중요한가요? |
| **일관성 vs 속도** | 코드 스타일 일관성과 빠른 기능 구현 중 우선순위는? |
| **사용자 편의 vs 보안** | 보안을 강화하면 사용자 경험이 불편해지는 부분은 어떻게 균형을 맞추나요? |
| **자체 개발 vs 외부** | 직접 구현하는 것과 기존 솔루션을 사용하는 것의 기준은? |
| **유연성 vs 성능** | 미래 확장을 위한 추상화와 현재 성능 최적화 중 무엇이 더 중요한가요? |

### 매핑된 클러리티 차원

| 차원 | 적용 우선순위 |
|---|:---:|
| `intent` | 매우 높음 (왜 이 트레이드오프?) |
| `outcome` | 높음 (어떤 결과를 우선?) |
| `scope` | 매우 높음 (MVP 경계) |
| `constraints` | 중간 |
| `success` | 높음 |
| `context` | 중간 |
| `non_goals` | **매우 높음** (트레이드오프의 본질 = 무엇을 하지 않는가) |
| `decision_boundaries` | **매우 높음** (어떤 트레이드오프는 자동, 어떤 것은 사용자 결정?) |

## 도메인 렌즈 적용 가능성 표 (Column Applicability Lookup)

`SKILL.md`의 **인라인 매트릭스 분류 체계**가 결정한 row(차원)에 대해, 어떤 column(렌즈)에서 질문을 골라야 하는지 결정적 조회:

| 차원 (Row) | 1순위 Lens | 2순위 Lens | 비고 |
|---|---|---|---|
| `intent` | UI/UX (사용자 의도) | 트레이드오프 (선택의 동기) | 기술 lens는 의도의 표면이므로 후순위 |
| `outcome` | 기술 (측정 가능 결과) | UI/UX (관찰 가능 결과) | 산출물 종류에 따라 |
| `scope` | 트레이드오프 (MVP 경계) | 기술 (시스템 경계) | 비목표 정의가 핵심 |
| `constraints` | 기술 (규모/성능/의존성) | 우려사항 (규정/SLA) | 일반 제약 vs 위험 제약 |
| `success` | 기술 (수용 기준) | UI/UX (UX 기준) | 검증 가능성이 핵심 |
| `context` | 기술 (브라운필드 코드베이스) | 우려사항 (브라운필드 위협 모델) | 그린필드는 이 차원 가중치 0 |
| `non_goals` | 트레이드오프 (안 하는 것) | 우려사항 (수용 안 하는 위험) | 명시적 비목표 |
| `decision_boundaries` | 트레이드오프 (자동 결정) | 우려사항 (위험 결정) | 누가 결정하는가 |

규칙:
1. row가 결정되면 1순위 lens에서 질문 시작
2. 1순위 lens가 적용 불가(예: UI 없는 작업) → 2순위 lens로 폴백
3. 양쪽 모두 적용 불가 → 차원에 적합한 일반 Socratic 질문 (예: "이 [차원]에 대한 구체적인 예시를 들어주실 수 있나요?")

## AskUserQuestion 사용 시 옵션 패턴

각 질문에 2-4개 선택지 + "직접 설명" 탈출구 추가. 자리표시자(`<...>`)는 실제 값으로 교체하세요:

```
question: "<여기에 구체적 질문>"
header: "<짧은 라벨>"           # ≤ 12 graphemes
options:
  - label: "<옵션 1>"             # ≤ 30 graphemes
    description: "<근거/장단점 1줄>"  # ≤ 100 graphemes
  - label: "<옵션 2>"
    description: "<근거/장단점 1줄>"
  - label: "<옵션 3>"
    description: "<근거/장단점 1줄>"
  - label: "직접 설명"
    description: "다른 답변/접근을 제안"
```

실제 사용 예시 ([SKILL.md "Question Primitive" 섹션](../SKILL.md) 참조):

```
question: "인증 방식으로 어떤 것을 선호하시나요?"
header: "인증 방식"
options:
  - label: "세션 기반"
    description: "서버에 세션 저장, 전통적이고 안정적"
  - label: "JWT 토큰"
    description: "토큰 기반, 확장성 좋음, 상태 비저장"
  - label: "OAuth 연동"
    description: "소셜 로그인 (Google, GitHub 등)"
  - label: "직접 설명"
    description: "다른 방식 제안"
```

Grapheme 길이 제약:
- `header` ≤ 12 graphemes (한글 음절 1개 = 1 grapheme; "아키텍처" = 4 graphemes, "인증 방식" = 5 graphemes 공백 포함)
- `label` ≤ 30 graphemes
- `description` ≤ 100 graphemes

## 도메인-적용 안내

이 질문 은행은 **참고용 패턴**입니다. 사용자 입력의 구체성에 따라 적응(adapt)하세요:
- 사용자가 이미 답변한 정보는 다시 묻지 않습니다 (트랜스크립트 검토)
- 브라운필드 작업에서 코드베이스로 답을 찾을 수 있는 사실은 `[from-code]` 라벨로 자동 확인 후 사용자에게는 결정/판단만 묻습니다
- 모든 lens의 모든 질문을 반드시 다 묻는 것은 아닙니다. row 우선순위 + 게이트 차단자 + 압력 패스 진행률에 따라 동적 선택
